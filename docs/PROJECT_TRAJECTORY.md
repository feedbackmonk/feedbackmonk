## Current Focus

**UI localization is DONE end to end (Stages 1 + 2, FR-FBR-34..40) - and still nothing has been translated.** That second clause is the load-bearing one: the machinery is complete and green, the content is deliberately empty, and `/1-translate` is the owner's release step (DEC-FBR-17). One catalog tree (`i18n/locales/<code>/<ns>.json`, five namespaces, `en` as source) feeds three runtimes through one generated locale table and one resolver - the widget's ~40-line `t()`, the SPA's i18next, and the `feedbackmonk-i18n` crate - with a shared 40-case resolution-fixture set all three execute. **Per-key English fallback is the shipped behavior**, so a missing translation renders English, never a raw key; that is why an untranslated catalog is safe to ship and why `translation-gap-status` (30 locales / 16,500 missing / DUE) is advisory rather than blocking. `i18n-literal-ratchet`'s baseline is now **0** - a new hard-coded user-facing literal in `widget/src` or `admin-ui/src` is a hard failure with nothing to hide behind.

**Three things to know before touching this area.** (1) The widget has **689 B of headroom** against its 30,720 B cap - Stage 2 spent 197 B of the previous 884. A documented `widget.`-prefix lever worth ~735 B is recorded in `widget/README.md`; spend it deliberately rather than discovering the ceiling by hitting it. (2) GitCellar vendors `widget/dist/` **by copy**, and `dist/locales/` is a directory in that tree - a re-vendor that copies only `widget.js` ships a widget whose lazy chunks 404 in every non-English locale while English keeps working, so the breakage is silent for the vendor and visible only to end users. `widget.js` moved again in Stage 2. That re-sync is filed to the GitCellar repo. (3) Locale values are attacker-reachable (`?lang=`, `localStorage`, `data-locale`) and steer `<html lang>`, `dir`, i18next and a dynamic `import()`; every lookup on a generated table now uses an own-property check, because the plain `in` operator and plain index reads both walk the prototype chain and `constructor` survived the canonicaliser. Seven such sites were closed - do not reintroduce one.

- **DEC-FBR-15/16/17 + DEC-FBR-IMPL-30/31** (this session, UI localization) - **15**: 31 locales ship from day one rather than a starter set, because the cost is the machinery, not the language count, and a per-locale rollout would relitigate the same design each time. **16**: initial language comes from the browser/OS preference, **never IP geolocation** - location is not language, and geo-guessing is both wrong more often and a privacy posture this product does not take. **17**: no translation runs automatically, ever - `/1-translate` on the owner's explicit word only; machine translation is a quota-spending, quality-bearing act, and legal/policy text must never be translated before its English is frozen. **IMPL-30**: the catalog is per-namespace files (`<code>/<ns>.json`), not one file per locale, so a surface loads only the namespace it needs. **IMPL-31**: an explicit language choice persists *per surface* - `tenants.locale` for the admin account, `feedback.submitter_locale` for the submitter, `localStorage fbm_lang` for an anonymous visitor on a tenant host, and the host page itself for the embedded widget - because those are four genuinely different identities, not one user in four places.
- **DEC-FBR-IMPL-23/24** (this session, sentiment + solicitation) — Two Stage 1 emergent decisions. **23** (sentiment granularity): the sentiment enum holds three states (negative|neutral|positive), not five (very_negative / negative / neutral / positive / very_positive) — finer granularity would require more labeling work without proportional signal gain; three states align with typical NPS-style surveys and are sufficient for initial trend analysis + agent decision-making. Widget selector is radial (clearer per-state affordance than radio buttons); submitter can change their mind mid-form. **24** (solicitation state machine locality): state is server-owned (not client-stamped), keyed by JWT-sub (same identity-anchor as work-order approvers), evaluated on every solicitation GET for freshness; `snoozed` auto-transitions to `pending` after cooldown elapses (checked server-side, not lazy-expired client-side).
